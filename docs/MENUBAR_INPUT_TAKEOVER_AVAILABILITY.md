# 菜单栏搬移怎样达到可用

2026-10-07，Asia/Shanghai；当前分支未提交、未安装。共有停止链路已实装，ANY用途没有变化。代码已通过离线生产注入和回归，真实搬移闭环仍未验收，backend禁用。本文供父线程和用户决定下一步契约，**不是策略改变或现场动作授权**。

当前工程可保证：操作绑定一个世代；停止状态不可由后续安静、回执或布局恢复清除；软件接受停止之后不再准入新的普通效果；每次session/PID投递单独检查，最多一项已经准入的效果在途。停止请求不等待系统调用或落盘完成。已准入、正在进入或执行中的效果可以完成；输入回调尚未交付时不能阻止已发生的竞争，不能保证物理输入与自动投递绝对互斥。

## 已完成的实际改动

- `MenuBarOperationStop`把显式取消、非自身输入、监听/健康失效、现有HID活动拒绝和执行失败汇到永久停止状态。取消provider只在绑定线程及作用域内调用；其他线程仍可请求停止。
- 发送链在witness落盘后、每次100ms回执等待、第二次PID投递前重查；每条route独立准入，第一条回执不能自动授予第二条。仍保留完整自身packet注册/单次匹配、权限检查、原100ms期限和现有ANY/age判断。
- 菜单打开后新增边界和取消检查；菜单关闭请求实际落盘前再经同一停止状态准入；move/open/restore入口、归位前后和清日志前均检查。接管后不会发新的关闭请求或逆向归位；已经准入的关闭请求可能完成。
- 不确定down不再触发隐式补发up或换route。保存绑定的down包、gesture、各可能执行route、upAttempted/pairDelivered/retained状态；up必须匹配同gesture/source/target/number/flags。`pairDelivered`只表示发送链返回，不证明物理按钮已释放或目标已处理成功。未知down阻止新发送和所有journal清理，原位几何不能免除责任；日志及原始packet-intent/possible-effect witness保留。自动cleanup尚未启用。

验证：493全量Swift；真实控制端及诊断编译条件各66项相关检查；44 Python；五个独立辅助入口typecheck。新增19项生产相关测试包含15项发送/停止注入及4项coordinator边界检查；不是上一轮15项抽象模型代替生产验证。独立复核发现的锁范围、取消闭包线程寿命、未确认down提前清日志问题已修正。[证据与保全](evidence/menu-bar-shared-stop-hardening-2026-10-07/README.md)。

源码已新增依赖，旧v15候选原样保留但**当前源清单预检拒绝**；不能将它称为新版可运行候选。本轮只做类型检查，没有重建签名包或启动它。后续试机前必须在独立路径构建、签名并通过完整新清单及原准入；这不等于安装正式版。

## 路线B的审批应具体到哪些变化

须明确告知并批准：ANY计数及age不再证明全物理静默；允许已交付观察与软件调度之外仍有未见/延后输入；允许一项已准入效果在停止后完成；一次停止可能留下移动后的图标、仍打开的菜单或未确认down，程序保留责任并不给出自动成功；未确认down只读保留，自动cleanup需要另一项明确契约。不能把“17类足够”当作这些风险已经消失。

批准必须覆盖**所有ANY关联判断**，不能只删一个if后仍被另一层age拒绝，也不能暗中豁免它们。最小明确影响面：

1. `MenuBarLocalContinuityLedger`中固定Q后的ANY一致性及对应age推断，从授权/停止条件改为诊断；真实本地请求仍要求原AppKit与tap精确回执及一次性来源绑定，不接受远程start。
2. `MenuBarRealLocalAuthorization`的双fence及末扫使用新契约证据，保持监听健康、序列/世代、固定期限、目标和一次性Permit。原250ms/3秒时间约束不靠换晚基线或延长等待“通过”。
3. `MenuBarListenOnlyInterferenceSource`中ANY age派生epoch/活动拒绝、旧publicActivityMatchesExactUp断言也需同一版本化政策；未匹配的tap事件仍无条件停止，禁止PID/marker近似归因。ANY完整原始值仍保存，不回填未知类型。

可验证替代应收敛到现有公开接口：确认当前tap实际允许的mask/健康；按公共all-events mask接收的未知类型仅作活动停止，不解析键内容、不新增私有API；增加明确范围的aggregate held-key/额外按钮补充以免把恒空keys当释放证明；安全输入或无法确认覆盖时拒绝；用当前位置和公开焦点/Space/显示通知及新鲜目标快照发现变化。它们合起来实现有限停止契约，仍检测不到所有短按或位置/焦点往返，不能再宣称全设备覆盖。

这是一次有限政策实施与验收，不需要先解释旧ANY-only的设备或类型：生产注入覆盖开始回执后活动、未知事件/失联、witness/回执/第二route取消、菜单接管、归位与未确认down；完成新源清单签名后，另行授权自建T/N一次move/menu/close/restore及取消/失败检查。现场发送次数、菜单状态、真实布局归位和journal责任必须有原始证据；停止后不得自动重试。通过自建目标后，再单独评审第三方和发布范围。

## 失败时明确怎样处理

未发送前拒绝：说明本轮条件/观察不足，零动作；只有原durable no-dispatch证明可清准备日志。已经有可能效果：停止新动作，保留日志和down责任，不用“界面看起来原位”宣称恢复。用户随后安静不重启本轮。正常完整归位仍需两份新鲜身份/布局/关闭证明和日志持久记录才清除。

恢复是新的明确请求、新世代和原严格恢复条件；未确认down存在时，即使布局原位也拒绝清除/逆向发送。当前没有可验证的自动down消除手段，不能承诺总能自动收尾；应将具体状态交给用户/受控测试应用处理，不伪造released状态。若产品要求任何物理输入都具有零竞争且停止后自动恢复一切，当前公开异步接口无法提供该保证，应选择路线C而不是继续卡在全局计数归因。

当前建议：接受本轮停止加固；父线程在A的可用性限制、B的明确有限风险、C的功能范围之间给出决定。无需再让用户保持静止或重复点击来解释ANY。
